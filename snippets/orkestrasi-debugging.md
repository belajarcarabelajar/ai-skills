> done inline without fan-out is permitted only when the cause is genuinely atomic
> and unambiguous, and the reason is written explicitly.

If RCA requires external library/RFC/upstream-issue evidence, run deep-research phase using templates/deep-research-report-template.md (see examples/deep-research-worked-example.md). Diagnose root cause (violated invariant + why), document the full RCA in .md log following templates/systematic-debugging-log-template.md including its Mermaid debugging-loop diagram (accTitle and accDescr are mandatory). Track investigation state in templates/progress-log-template.md. HARD GATE: await explicit approval of the RCA before patching; no code without approval gate.

INVESTIGATION IS SUBAGENT-FIRST, MANDATORY. For anything beyond a single obvious one-file cause, you are the ORCHESTRATOR of the investigation, not its only worker. Do NOT trace the whole call stack, read every call site, and grep every log yourself inline. Use this pipeline: (1) TASK-CHUNKING — split the investigation into the smallest independently verifiable units, one per hypothesis: one candidate root cause, one caller chain, one log slice, one failing-test variant, one config/source-of-truth surface. Chunk by HYPOTHESIS, not by file, so parallel work tests competing explanations in parallel instead of serially. (2) BATCH MANIFEST — before dispatch write the manifest: chunk id, hypothesis under test, files or commands in scope, expected output (a verdict: confirmed / disproven / inconclusive with evidence), and the verification command. Every candidate cause must be covered and every chunk must have exactly one owner; overlapping write scopes are an orchestration defect to fix BEFORE dispatch. (3) HIGH FAN-OUT FLOOR — dispatch narrow subagents in one wide batch and target 10 or more when the investigation plausibly supports it. A wide bug surface, a regression touching many callers, or an intermittent failure with many candidate causes all fan out wide. Async-dispatch the full batch when the runtime allows and keep doing safe independent parent-side work meanwhile. Ten narrow investigators strictly beat one overloaded investigator: hypotheses get tested in parallel, a disproven cause is discarded without contaminating the others, and each report stays readable. (4) NON-OVERLAPPING SCOPES — give each subagent a disjoint file set, log slice, or hypothesis. Two subagents must never edit or claim the same file. Isolate in worktrees or branches when read-write overlap is unavoidable. (5) NESTED FAN-OUT — a subagent whose chunk still contains independent candidate causes must itself chunk and fan out rather than absorb the whole search. (6) GATHER & SYNTHESIZE at a defined review checkpoint — subagent reports are INPUTS, never conclusions: collect all of them, then dedupe overlapping findings, drop restatements, resolve contradictions from the underlying evidence (a diff, an exit code, a log line), independently verify each surviving claim yourself, and carry only confirmed findings into the RCA. NEVER concatenate raw reports as the diagnosis. (7) PARENT DIFF AUDIT GATE — never accept a subagent's "root cause found" or "fixed" claim on trust; inspect git diff and re-run the repro yourself in the parent before accepting it. Re-dispatch ONLY the failing or disproven chunk; never restart the whole batch for one red chunk. (8) BATCH THE INVESTIGATION — run the dispatched batch as one round, not one investigator at a time.

INLINE INVESTIGATION IS A DOCUMENTED EXCEPTION, NEVER A DEFAULT. Investigating inline yourself is allowed only when the cause is genuinely atomic and obvious (a single stack trace with an unambiguous line, a typo, a missing import) or when no subagent tool exists in this runtime, and you must state that reason explicitly. "The stack trace is short" is NOT a valid reason: a short trace with several plausible causes is exactly the case that fans out best. SHOTGUN DEBUGGING IS PROHIBITED — no speculative parallel edits, no changing code to see what happens, and no fixing symptoms before the root cause is isolated with a reproducing failing test.

FIX VERIFICATION IS ALSO FAN-OUT. After the patch, dispatch subagents to independently re-run the repro test, re-run the neighboring regression suite, audit every sibling caller of the changed function for breakage, and review the diff for the 8 qualification criteria per templates/code-review-template.md. These are independent checks and belong in one batch, not in one sequential pass.

MUST write a per-chunk contract per templates/subagent-contract-template.md: scope, exact inputs, expected output, verification method, review checkpoint. Propagate enough context that an investigator never guesses an invariant it cannot see, and never route a chunk to a subagent you could not do yourself. Apply smallest safe localized fix (no unrelated refactor) after the RCA approval gate, classify the failure (code/test/contract/environment/infrastructure/pre-existing) in the Error Ledger, then verify: repro test GREEN plus targeted regression suite with 0 failures, fresh evidence shown. Close the session with the Session-Close Debt Sweep (Step 6 of the skill): raise every debt from this investigation (code that is still hardcoded, a sibling caller that was never touched, a test that is still flaky, a pre-existing warning, a Root Cause that was never removed systematically, a documentation gap), rank the 3-5 follow-ups that can be completed right now, then inject ONE multi-select QUESTION SET (checkboxes) through the harness question/ask feature after the final recap, never a plain text report instead. Each selected item is executed through the full pipeline (chunk, subagent fan-out, TDD, verification, diff audit, commit); each rejected or over-cap item is written to the follow-up backlog with the marker `defer: <ceiling>, <upgrade-trigger>`. Make sure to remember this skill while we are working in this session. Feel free to re-call this skill in every checkpoint. Always save result of investigation and fix in .md format.
