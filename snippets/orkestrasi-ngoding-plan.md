If decision depends on external library/RFC/ecosystem evidence, first run deep-research phase using templates/deep-research-report-template.md (see examples/deep-research-worked-example.md); otherwise skip directly to plan. Generate implementation plan following templates/implementation-plan-template.md with ultra-plan/v1 frontmatter (tasks[].id, depends_on DAG, skip_if, verify_exit). Every plan MUST include at least one valid Mermaid flowchart: node = setiap task id, panah = setiap depends_on edge (A --> B berarti B depends_on A), plus approval gate dan Verify tail; node id harus identik dengan tasks[].id dan heading Task <id>; setiap diagram wajib punya accTitle dan accDescr. Save plan to docs/code-plan/plans/YYYY-MM-DD-<feature>.md (design doc bila ada ke docs/code-plan/specs/). Validate with bun scripts/ultra-plan-runner.mjs <plan.md> dan bun scripts/validate-skill.mjs. HARD GATE: no implementation, no scaffolding, no code until plan disetujui eksplisit.

📤 PLAN PUBLISH GATE — the plan is published when the plan is FINISHED, not when it is approved. Run these three steps in this order, and do not skip step 1 because approval feels close: (1) IMMEDIATELY after `bun scripts/ultra-plan-runner.mjs <plan.md>` prints `Validation: OK`, and BEFORE asking for approval, run `bun scripts/plan-publish.mjs <plan.md>` from the ai-skills repository (that is where the publisher and plans.publish.json live, whatever project owns the plan). This puts the plan in the Obsidian vault at status `Draft` while the human is still deciding, so the review happens where they are looking instead of only in a repository directory. (2) Run the same publisher again after approval and BEFORE `bun scripts/ultra-plan-runner.mjs <plan.md> --execute`, so the mirror carries the approved state. (3) AFTER execution and AFTER the Session-Close Debt Sweep, close the plan: apply the task ticks with `bun scripts/plan-mark-done.mjs <plan.md> --from <runner.log>` — capture the runner's output to a log first, because the ticks are applied from what the runner actually recorded, and a task it recorded as `NEEDS-AGENT`, `HALTED-UPSTREAM` or `FAILED-*` is deliberately left unticked; then set `status: Complete` in the plan's own frontmatter; then run the publisher a third time. Without step 3 the mirror keeps showing the step-2 snapshot, so a finished plan reads `Draft` in the vault forever — that is a known, measurable state, not a bug to guess at. `SKIPPED-IDEMPOTENT` is a pass, not a failure — the plan was unchanged, so nothing was written and nothing was staged; do not go investigate a non-problem. One-way: the project repository is the source of truth, the vault copy is a read-only mirror, and a mirrored note is never hand-edited. THEREFORE apply the ticks in the SOURCE plan and write every review verdict into the SOURCE plan's approval section, never into the mirror: the next publish overwrites the mirror, so anything written there is erased without warning. The gate is enforced, not advisory: `ultra-plan-runner --execute` refuses to run any plan whose vault mirror is missing or stale and exits 3, so a skipped publish fails loudly instead of silently. If you genuinely must execute without publishing, pass `--skip-mirror-gate`; it prints a warning every single time it is used.

EXECUTION IS SUBAGENT-FIRST, MANDATORY. After approval you are the ORCHESTRATOR, not the main implementer. Do NOT write the feature yourself inline. Follow this pipeline exactly, in this order: (1) TASK-CHUNKING — before the first mutation, decompose the plan into the smallest independently verifiable chunks (one behavior, one file, one command chain, one review surface); any chunk that does not fit one subagent's context is split again. (2) BATCH MANIFEST — write the dispatch manifest first: chunk id, owner, target files, expected output, verification command. Every planned unit must be covered and every chunk has exactly one owner; overlapping write scopes are an orchestration defect to fix BEFORE dispatch, not to discover in the diff. (3) HIGH FAN-OUT FLOOR — dispatch narrow subagents in one wide batch, targeting 10 or more when the task plausibly supports it; dispatch the full batch asynchronously when the runtime allows, and continue safe independent parent-side work while they run. Ten narrow subagents strictly beat five overloaded ones: faster, isolated failures, readable reports. (4) NON-OVERLAPPING WORKSPACES — give each subagent strictly disjoint target files, or isolate them in worktrees/branches, so parallel writes cannot conflict. (5) NESTED FAN-OUT — a subagent whose chunk still contains independent sub-work must itself chunk and fan out instead of absorbing the whole scope. (6) GATHER & SYNTHESIZE at a defined review checkpoint — subagent reports are INPUTS, never conclusions: collect all of them, then dedupe overlaps, drop restatements, resolve contradictions from the underlying evidence, independently verify each claim (git diff, exit code, log), and carry only new findings and evidence into the task state. NEVER concatenate raw reports as your answer. (7) PARENT DIFF AUDIT GATE — never accept a subagent's self-reported success; inspect git diff and re-run targeted tests yourself in the parent before integrating. Re-dispatch ONLY the failing chunk, never restart the whole batch for one red chunk. (8) BATCH THE SELECTIONS — run the whole dispatched batch as one round, not one subagent at a time.

INLINE EXECUTION IS A DOCUMENTED EXCEPTION, NEVER A DEFAULT. Working inline yourself is allowed only for a genuinely atomic task or when no subagent tool exists in this runtime, and you must state that reason explicitly at the handoff. "The task is small" is NOT a valid reason: small total work means MORE chunks, not fewer subagents.

TASK SIZE IS NOT AN EXCUSE TO SKIP FAN-OUT. If the plan has only 2-3 tasks but each spans many files, chunk by FILE and by BEHAVIOR until 10+ narrow chunks are plausible. If you end up with fewer than the floor, write the reason explicitly: atomic task, no subagent runtime tool, or shared mutable state that cannot be split.

Every delegated chunk needs a written contract per templates/subagent-contract-template.md: clear scope, exact inputs, expected output, verification method, and review checkpoint. Propagate enough context that a subagent never has to guess an invariant it cannot see, and do not route a chunk to a subagent that you could not do yourself.

After approval, execute per task with TDD (RED: failing test dulu → GREEN: minimal code → REFACTOR); bug pakai systematic-debugging (reproduce → diagnose → smallest fix → regression proof) dan WAJIB fan-out sub-agent per pipeline di atas, termasuk untuk search, trace caller, dan reading log panjang. Before completion claim, run fresh verification (test/lint/typecheck/build yang relevan, exit 0 dengan 0 failures/errors/warnings) dan tunjukkan buktinya. Finish with git status, hapus file sementara, commit conventional atas nama Iwan Kurniawan tanpa co-author trailer. Tutup sesi dengan Session-Close Debt Sweep (Step 6 of the skill): angkat semua utang yang terlihat selama planning dan eksekusi (defer ceiling yang tercapai, temuan review, pre-existing warning, sibling caller yang belum konsisten, test layer yang kurang, TODO/skip/ts-ignore, gap verifikasi), rank 3-5 follow-up yang bisa diselesaikan sekarang juga, lalu inject SEBUAH satu QUESTION SET multi-select (checkbox) lewat fitur question/ask milik harness setelah recap akhir, jangan pakai teks laporan saja. Item terpilih dieksekusi sebagai pekerjaan sungguhan (chunk, subagent fan-out, TDD, verifikasi, diff audit, commit) dan plan ditutup `Complete` hanya setelah sweep ini jalan; item yang ditolak atau di luar cap ditulis ke backlog follow-up di plan dengan marker `defer: <ceiling>, <upgrade-trigger>`.
